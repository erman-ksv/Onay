# Onay — подготовленный тестовый сервер

Этот набор запускает отдельные API/PostgreSQL и HTTPS-прокси Caddy. Это конфигурация для подготовки staging, не уже развёрнутый сервер. Docker-образ включает зафиксированные lockfile зависимости и инструменты миграции. Он пока не оптимизирован как минимальный release-образ. Production-код приложения не изменяется.

## Что потребуется для настоящего запуска

Linux x86_64 сервер с Docker/Compose, домен с DNS на этот сервер, открытые80/443, достаточно диска для PostgreSQL и отдельная новая тестовая БД. Хостинг/домен пока не выбраны; покупка или автоматическое развёртывание не выполнялись. Рецепт сохраняет существующие linux-x64 ограничения зависимостей.

Скопировать `.env.example` в `deploy/onay/.env`, установить права600 и заполнить домен, email для сертификата, телефон администратора и два разных случайных секрета. Для каждого секрета отдельно выполнить:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

POSTGRES_PASSWORD должен быть отдельной hex-строкой32–128 символов, SESSION_SECRET — отдельным случайным значением не менее32 символов. Завершённый `.env` не коммитить и не присылать в чат. Docker build исключает env-файлы и ключи. Не запускать `compose config` с выводом значений; для проверки синтаксиса использовать `config --quiet`.

## Запуск из корня репозитория

```sh
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env config --quiet
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env build api
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env up -d --wait db
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env run --rm migrate
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env up -d --wait api
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env --profile edge up -d edge
```

Применяются версионированные миграции, без `push-force`. Перед миграцией существующей базы нужен отдельный проверенный план и backup; этот сценарий рассчитан на новую тестовую БД. Для остановки без удаления данных использовать `docker compose ... down` без `--volumes`. Named volume pgdata сохраняет данные. Внешние порты API и PostgreSQL не публикуются; доступ снаружи проходит через Caddy. Socket.IO обслуживается тем же reverse_proxy.

Caddy получает сертификат для реального домена автоматически, когда DNS и80/443 доступны. Проверять `https://ваш-домен/api/healthz` с обычной проверкой TLS, без `-k`. HTTPhealthz — liveness приложения; он не является полной проверкой текущей доступности БД. PostgreSQL имеет отдельный pg_isreadyhealthcheck. Сквозное чтение БД и восстановление сессии проверяются smoke-сценарием.

API и миграции запускаются от node, с read-onlyfilesystem, временным/tmp и сброшенными capabilities. Старт останавливается при development/memory-режиме, выключенном одобрении водителей, слабых или повторно использованных секретах. Secrets передаются только при запуске, не как build args. Владельцу Docker-хоста доступны environment контейнеров; доступ к хосту должен быть ограничен.

## Что проверяется в CI

Изолированный случайный Compose-проект без публичных портов: настоящий Dockerbuild, PostgreSQL, повторное безопасное применение миграций, productionboot, отрицательные проверки конфигурации, авторизованный API-запрос к данным, та же JWT-сессия после перезапуска API и БД, отсутствие demoOTP вproduction и валидность Caddyfile. Для сессии используется только синтетический пользователь внутри одноразовой CIбазы; новый обход авторизации в API не добавляется. CIсам создаёт и очищает только свои временные volumes. Локальный smokeCLI запрещён, чтобы случайно не очищать чужую staging-среду.

CI не получает публичный сертификат, не разворачивает постоянный сервер и не отправляет настоящую SMS. Отчёт явно сохраняет эти три результата как false. Node-модуль smoke не является штатным инструментом для работы с реальными пользователями.

## Открытые условия приёмки APK

Нужны фактически выбранный хостинг/домен, развёртывание, проверка TLS с телефона и productionSMS. В текущем приложении нет подключённой настоящей SMS-доставки: production скрывает OTP, поэтому успешный запуск API ещё не даёт реального входа с телефона. DevelopmentOTP на публичном productionсервере не включать. Внешний подвоз также требует реально настроенного roadroutingпровайдера. Администратор задаёт реальные точки маршрута. Финальные устройства/GPS, backup/restore, нагрузка, мониторинг, подпись релиза и юридическая приёмка остаются отдельными.
