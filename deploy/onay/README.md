# Onay — подготовленный тестовый сервер

Этот набор запускает отдельные API/PostgreSQL и HTTPS-прокси Caddy. Это конфигурация для подготовки staging, не уже развёрнутый сервер. Docker-образ включает зафиксированные lockfile зависимости и инструменты миграции. Он пока не оптимизирован как минимальный release-образ. Production-код приложения не изменяется.

## Что потребуется для настоящего запуска

Linux x86_64 сервер с Docker/Compose, домен с DNS на этот сервер, открытые80/443, достаточно диска для PostgreSQL и отдельная новая тестовая БД. Хостинг/домен пока не выбраны; покупка или автоматическое развёртывание не выполнялись. Рецепт сохраняет существующие linux-x64 ограничения зависимостей.

Скопировать `.env.example` в `deploy/onay/.env`, установить права600 и заполнить домен, email для сертификата, телефон администратора и два разных случайных секрета. Для каждого секрета отдельно выполнить:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

POSTGRES_PASSWORD должен быть отдельной hex-строкой32–128 символов, SESSION_SECRET — отдельным случайным значением не менее32 символов. Завершённый `.env` не коммитить и не присылать в чат. Docker build исключает env-файлы и ключи. Не запускать `compose config` с выводом значений; для проверки синтаксиса использовать `config --quiet`.

## Запуск из корня репозитория

```sh
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env config --quiet
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env build api
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env up -d --wait db
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env run --rm migrate
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env up -d --wait api
docker compose -f deploy/onay/compose.yaml --env-file deploy/onay/.env --profile edge up -d edge
```

Применяются версионированные миграции, без `push-force`. Перед миграцией существующей базы нужен отдельный проверенный план и backup; этот сценарий рассчитан на новую тестовую БД. Для остановки без удаления данных использовать `docker compose ... down` без `--volumes`. Named volume pgdata сохраняет данные. Внешние порты API и PostgreSQL не публикуются; доступ снаружи проходит через Caddy. Socket.IO обслуживается тем же reverse_proxy.

Caddy получает сертификат для реального домена автоматически, когда DNS и80/443 доступны. Проверять `https://ваш-домен/api/healthz` с обычной проверкой TLS, без `-k`. HTTPhealthz — liveness приложения; он не является полной проверкой текущей доступности БД. PostgreSQL имеет отдельный pg_isreadyhealthcheck. Сквозное чтение БД и восстановление сессии проверяются smoke-сценарием.

API и миграции запускаются от node, с read-onlyfilesystem, временным/tmp и сброшенными capabilities. Старт останавливается при development/memory-режиме, выключенном одобрении водителей, слабых или повторно использованных секретах. Secrets передаются только при запуске, не как build args. Владельцу Docker-хоста доступны environment контейнеров; доступ к хосту должен быть ограничен.

## Что проверяется в CI

Изолированный случайный Compose-проект без публичных портов: настоящий Dockerbuild, PostgreSQL, повторное безопасное применение миграций, productionboot, отрицательные проверки конфигурации, авторизованный API-запрос к данным, та же JWT-сессия после перезапуска API и БД, отсутствие demoOTP вproduction и валидность Caddyfile. Для сессии используется только синтетический пользователь внутри одноразовой CIбазы; новый обход авторизации в API не добавляется. CIсам создаёт и очищает только свои временные volumes. Локальный smokeCLI запрещён, чтобы случайно не очищать чужую staging-среду.

CI не получает публичный сертификат, не разворачивает постоянный сервер и не отправляет настоящую SMS. Отчёт явно сохраняет эти три результата как false. Node-модуль smoke не является штатным инструментом для работы с реальными пользователями.

## Открытые условия приёмки APK

Нужны фактически выбранный хостинг/домен, развёртывание, проверка TLS с телефона и productionSMS. В текущем приложении нет подключённой настоящей SMS-доставки: production скрывает OTP, поэтому успешный запуск API ещё не даёт реального входа с телефона. DevelopmentOTP на публичном productionсервере не включать. Внешний подвоз также требует реально настроенного roadroutingпровайдера. Администратор задаёт реальные точки маршрута. Финальные устройства/GPS, нагрузка, мониторинг, подпись релиза и юридическая приёмка остаются отдельными.


## Резервная копия и проверка восстановления

Запускать с корня репозитория. Каталог для архивов создать вне checkout на защищённом диске с правами700; в примере `/srv/onay-backups` уже создан и доступен текущему пользователю. Указать фактическое имя Compose-проекта (в этом рецепте `onay-staging`). Требуются Node22+ и доступ к Docker. Отдельный `pg_dump` на хосте не нужен: используется клиент PostgreSQL16 внутри db-контейнера.

```sh
node deploy/onay/backup.mjs create deploy/onay/.env onay-staging /srv/onay-backups/onay-2026-10-24.dump
node deploy/onay/backup.mjs verify deploy/onay/.env onay-staging /srv/onay-backups/onay-2026-10-24.dump
```

`create` сохраняет согласованный snapshot pg_dump custom-format с правами600, отказывается перезаписывать файл/симлинк, удаляет незавершённый архив при ошибке. Имя должно быть новым для каждой копии. Вывод содержит только размер и SHA256; сохранить checksum отдельно от файла для последующей проверки целостности. Checksum не шифрует и не аутентифицирует данные. Архив содержит персональные данные и требует защищённого хранения; не отправлять его в GitHub/чат. Копии `.dump` исключены из Dockerbuild.

`verify` создаёт **отдельную случайную** базу `onay_restore_*` через template0, выполняет pg_restore в одной транзакции с остановкой при ошибке и удаляет только эту созданную базу в finally. Существующие `onay`/pgdata не перезаписываются. Проверять только доверенные собственные архивы: PostgreSQLdump может содержать исполняемые SQLкоманды. Нужны дополнительное место и ресурсы для полной копии; проверку планировать вне пика. При жёстком завершении процесса/хоста временная база может остаться; проверять её происхождение перед ручным удалением.

CI проверяет настоящую копию и восстановление: исходный пользователь присутствует в восстановленной базе, добавленный после копирования — отсутствует. Проверяются права600, запрет перезаписи, отказ на повреждённом архиве, удаление временных баз и сохранение данных/сессии исходного API. Архивы и персональные данные в CIартефакты не загружаются.

Переключение рабочего API на восстановленную базу — отдельная операция после проверки данных; этот инструмент переключение не выполняет. Сервер ещё не развёрнут. Расписание и ограничение локальных копий описаны ниже; зашифрованная внешняя копия и внешние оповещения пока не настроены.

## Ежедневные автоматические копии на Linux/systemd

`backup-schedule.mjs run` создаёт копию, проверяет её настоящим восстановлением в отдельную базу и сохраняет manifest с SHA256. Только после этого удаляются старые завершённые пары archive/manifest сверх ONAY_BACKUP_KEEP (по умолчанию7, минимум2). Чужие файлы, незавершённые и непроверенные копии не удаляются; их нужно разбирать отдельно. При сбое предыдущие копии и lastSuccess сохраняются, процесс завершается ненулевым кодом. Ошибки не содержат секретов/строк БД.

`backup-schedule.mjs status` завершается ненулевым кодом, если последняя попытка провалена, нет успешной копии, архив/manifest отсутствует или копия старше ONAY_BACKUP_MAX_AGE_HOURS (по умолчанию36). Это локальная проверка для внешнего мониторинга; доставка оповещений ещё не подключена. SHA256 сохраняется для ручной проверки, status не перечитывает содержимое большого архива.

Сначала нужен реально развёрнутый сервер из предыдущего раздела, Node22+ в стандартном PATH systemd (`/usr/local/bin:/usr/bin:/bin`), systemd, Docker/Compose и репозиторий в `/opt/onay`. В recipe нет подключения к DockerAPI по сети. Указанный сервисный пользователь получает Dockerдоступ, который фактически даёт управление хостом: использовать только выделенный доверенный сервер. Убедиться, что user `onay-backup` существует, входит в группу docker, может читать исходники и Compose.env, а `/srv/onay-backups` принадлежит ему и имеет права700. Секретный Compose.env — права600, владелец onay-backup; в backup.env только пути/настройки.

Установить файлы **на выбранном сервере**, после проверки фактических путей/имени проекта (эти команды в текущей работе не выполнялись):

```sh
sudo install -d -m 750 -o root -g onay-backup /etc/onay
sudo install -d -m 700 -o onay-backup -g onay-backup /srv/onay-backups
sudo install -m 640 -o root -g onay-backup deploy/onay/systemd/backup.env.example /etc/onay/backup.env
sudo install -m 644 deploy/onay/systemd/onay-backup.service /etc/systemd/system/onay-backup.service
sudo install -m 644 deploy/onay/systemd/onay-backup.timer /etc/systemd/system/onay-backup.timer
sudo systemd-analyze verify /etc/systemd/system/onay-backup.service /etc/systemd/system/onay-backup.timer
sudo systemctl daemon-reload
sudo systemctl start onay-backup.service
sudo systemctl enable --now onay-backup.timer
sudo systemctl list-timers onay-backup.timer
```

Первую ручную serviceпопытку проверить через `systemctl status onay-backup.service` и `journalctl -u onay-backup.service`; только после успеха включать timer. Расписание: ежедневно02:30UTC с задержкой до15минут; Persistent догоняет пропущенный запуск после включения сервера. Systemd не запускает один service одновременно; дополнительный lock защищает прямые вызовы runner. При SIGKILL/отключении питания lock может остаться: перед ручным удалением `/srv/onay-backups/.onay-backup.lock` убедиться, что старый процесс больше не работает. Никогда не удалять pgdata.

Проверка свежести без доступа к БД:

```sh
sudo -u onay-backup env ONAY_BACKUP_DIRECTORY=/srv/onay-backups /usr/bin/env node /opt/onay/deploy/onay/backup-schedule.mjs status
```

Это локальные копии на одном диске, не защита от потери сервера. Нужны зашифрованное внешнее хранение, retention там, отдельная проверка восстановления и внешние оповещения. Конфигурация готова к проверке; timer на настоящем сервере ещё не установлен/не включён. CI валидирует unitфайлы и выполняет реальные циклы runner, включая остановку PostgreSQL, сохранение старых копий, обнаружение сбоя и восстановление работы.


## Настоящий SMS-вход

Подготовлено подключение [DevSMS](../../docs/ONAY_DEVSMS_SETUP.md). Отправка по умолчанию выключена отдельным флагом, ключ передаётся только API. Без SMS-провайдера production возвращает503 вместо ложного подтверждения отправки; smoke проверяет это и отсутствие созданного OTP. Публичная доставка и работающий сервер этим не подтверждаются. Не включать отправку в автоматических проверках и не расходовать пробные SMS.
