# TezJet 2.8 — защита OTP, отчёт этапа

Исходная база: `main@cf1a38c0a499264579e0a39de5716cf2b3cf974a`, объединённый PR #36. Работа в `feat/otp-protection-20261014`. Область — backend, PostgreSQL и API авторизации. Пункт 6.1 ведёт другой исполнитель; фронтенд ждёт макет пользователя, Agent-Factory отложен.

## Анализ до изменений

Два независимых read-only аудита изучили контроллер, оба Store, схему, миграции, middleware, тесты и CI. Найдено:

- Отправка OTP без паузы и квоты безусловно заменяла действующий код.
- Неверные попытки не учитывались; перебор был возможен до конца TTL.
- `/auth/login` и `/auth/verify-otp` требовали одного бюджета.
- `normalizePhone` допускал пустые или недоставляемые номера после удаления символов.
- Ограничения должны переживать рестарт и разделяться между экземплярами API.
- MemoryStore и PostgreSQL расходились на точной границе истечения OTP.
- Проверка лимита после JSON parser не охватывала повреждённые и слишком большие тела запросов.

Сохранены существующие свойства: криптографическая генерация OTP, HMAC в PostgreSQL, одноразовое потребление кода, политика инвалидирования прежних токенов и запрет повышения роли до admin.

## Реализация

- Общий бюджет трёх OTP endpoints по IP до разбора тела: 120 запросов за 15 минут по умолчанию. Недопустимые поля, malformed JSON, превышение размера и отклонённые запросы также учитываются.
- По телефону: пауза 60 секунд, максимум 5 выдач за часовое окно; отклонённая выдача сохраняет предыдущий код.
- Пять неверных кодов за 15 минут блокируют номер на 15 минут. Первые четыре ошибки — 401; пятая и запросы во время блокировки — 429. Правильный код и повторная отправка во время блокировки также запрещены.
- Повторная выдача, роль, язык и смена адреса проверки не сбрасывают счётчики. Успешная проверка сбрасывает только телефонный бюджет ошибок, сохраняя квоты отправки и IP.
- Счётчики PostgreSQL сохраняются отдельно от challenge. Телефонные операции берут одни и те же строки в устойчивом порядке, используют время БД после ожидания блокировок и коммитят неверные попытки.
- IP берётся из `request.ip`, без доверия к переданным заголовкам. IPv4 и mapped IPv6 имеют общую корзину; IPv6 группируется по `/64`. Идентификаторы корзин — HMAC, без открытых телефонов/IP.
- Ответ ограничения: `429 OTP_RATE_LIMITED`, `Retry-After`, `retry_after_seconds`. Ошибка защитного хранилища: `503 OTP_STORAGE_UNAVAILABLE`, без продолжения авторизации и без SQL-параметров в логе.
- Очистка просроченных данных ограничена пакетами по 100; PostgreSQL использует `SKIP LOCKED` и сохраняет активные блокировки.
- Миграция `0005_otp_protection` добавляет таблицу и индексы, сохраняя прежние challenges. Настройки лимитов проверяются при запуске; отключения по test/development нет.

Все параметры и требования к reverse proxy описаны в README API. Перед запуском обновлённого сервера требуется миграция. При текущем `trust proxy=false` клиенты за reverse proxy разделяют его IP-квоту; настройка доверенных адресов proxy относится к deployment.

## Проверки после изменений

Пройдено локально: проверки канонизации номера и IP, валидации кода, ответа 429, MemoryStore (пауза, квоты, блокировка, повторная выдача, точное истечение, одноразовое потребление, освобождение после блока), а также синтаксис изменённых тестов и `git diff --check`.

Независимое ревью нашло порядок middleware; исправление перепроверено. После исправления конкретных блокеров в логике Store, SQL, middleware и валидации не обнаружено.

Добавлен `otp-limits.test.mjs`: 19 основных тестов и 4 вложенные проверки. Настоящий PostgreSQL, реальный API-код (окружение тестов) и реальные блокировки; обе последовательности правильного/неверного OTP, истечение неизменного кода во время ожидания, сохранение квот, рестарт и два процесса API, ошибка БД, миграция и конфигурация. Семь прежних приватных схем дополнены таблицей квот; fixtures меняют только cooldown в своей схеме.

**Первый CI успешно прошёл: 219/219 тестов, 0 ошибок и пропусков, TypeScript и миграции.** Проверка выполнена на PostgreSQL 16 и Node 22 для `f88d6ef83dc6a366e204c6f8aac9211e849e0fc6`: [CI](https://github.com/erman-ksv/TezJet/actions/runs/38649565529). [Браузерная проверка маршрутов водителя](https://github.com/erman-ksv/TezJet/actions/runs/38649565261) также прошла, включая API и Expo regressions.

Первый Admin QA обнаружил, что повторный вход после reload запрашивал новый OTP раньше 60 секунд. Исправлен только сценарий проверки: он ждёт оставшуюся паузу по монотонным часам, по-прежнему требует настоящие 202/200 и сохраняет лимиты сервера. Локально прошли `py_compile` и семь проверок ожидания с подменёнными часами. Полный CI и Admin QA запускаются после этой правки; актуальные результаты окончательного HEAD находятся в [PR #37](https://github.com/erman-ksv/TezJet/pull/37/checks). Это запись подтверждённых результатов, а не обещание успешного последующего прогона.
