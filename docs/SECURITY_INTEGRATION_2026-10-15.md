## Разрешение пересечений кода

В `app.ts` логгер с безопасной сериализацией и серверным request ID остаётся перед остальными обработчиками. OTP gate выполняется до JSON и URL-encoded parser, поэтому повреждённое или слишком большое тело OTP-запроса также расходует IP-бюджет. После parser работают маршруты, JSON404 и единый безопасный error handler.

Отдельный OTP parser error handler заменён общей классификацией ошибок тела. Для OTP и остальных API действуют единые коды: `400 INVALID_JSON`, `413 PAYLOAD_TOO_LARGE`, `415 UNSUPPORTED_MEDIA_TYPE`. Это сохраняет ограничения OTP и одновременно исключает различие публичных parser-контрактов между двумя PR.

В `storeContract.ts`, MemoryStore и PostgreSQL совмещены защищённые операции OTP и операции настроенных маршрутов. Методы и проверки маршрутов из main сохранены вместе с отдельными счётчиками OTP, транзакциями и блокировками PostgreSQL. Миграция `0005_otp_protection` добавляет таблицу квот и индексы; перед запуском обновлённого сервера требуется применить миграции.

Ответ `429 OTP_RATE_LIMITED` сохраняет `Retry-After` и `retry_after_seconds` и теперь содержит серверный `request_id`, совпадающий с `X-Request-Id`. Это относится и к раннему отклонению IP gate до parser, и к ограничению телефона в контроллере. Входной `X-Request-Id` не принимается как серверный идентификатор.

## Проверки интеграции

Приватные PostgreSQL-схемы тестов маршрутов и безопасных ошибок дополнены таблицей `otp_rate_limits`. Тесты создают изолированные таблицы с настоящими столбцами и индексами; лимиты работающего приложения для этих сценариев не отключаются.

OTP-регрессии согласованы с общими parser-кодами и безопасным текстом ошибки защитного хранилища. Проверки `request_id` и `X-Request-Id` охватывают телефонное ограничение и gate перед parser, включая отклонение подменённого входного идентификатора.
