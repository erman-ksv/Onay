# Driver vehicle and revision-bound administrator review

Drivers may read and submit their own vehicle with authenticated driver mode, including while waiting for approval: GET/PUT `/api/driver/vehicle`. Required data: make, model, plate_number, passenger seat_capacity (1–8, excluding driver). PUT requires `expected_revision: null` for the first profile or the last server receipt for edits. Extra server-owned fields, invalid capacity/plate/name and stale revisions fail without mutation.

A nullable JSONB column `tezjet_users.driver_vehicle` is added by migration 0008; existing accounts are not rewritten. Both stores implement the same rules. A save generates a server revision and sets driver approval to pending atomically. Queue enrollment (including a retained departed entry), pending offers and active rides prevent edits. PostgreSQL uses the existing queue-before-user lock order; joins recheck the live reviewed capacity and approval after their user SHARE lock. Failed joins roll back entry insertion. An administrator decision locks the user and requires `expected_vehicle_revision` matching the displayed car, so concurrent edits cannot approve unseen data.

The driver form submits the exact current receipt and preserves an explicit conflict until refresh. The admin directory displays the car, plate and passenger capacity, with approve/reject controls bound to the displayed revision. Passenger contact includes only public car fields after current driver approval and an accepted active assignment. Private receipt/update metadata is not sent to passengers. Capacity at queue join cannot exceed the reviewed car. Existing seat reservations and fares are unchanged.

Compatibility: accounts with no vehicle keep their pre-existing approval/queue contract; legacy admin API calls without a vehicle receipt remain valid only when there is no saved vehicle. The normal new admin vehicle controls require a submitted car. This stage does not make car submission mandatory for the whole existing fleet. A submitted car cannot use this compatibility path to bypass review, including with the development driver-approval switch disabled.

Administrator review is manual, not an external plate/ownership/KYC registry verification. Vehicle photos, document upload and country-specific registration validation are separate work. No production migration/deployment is performed by this PR.

Verification covers real PostgreSQL persistence, validation/ownership/revocation, exact review revision, capacity rollback, busy edits, concurrent review/edit and join/edit, and MemoryStore parity. Mobile validation/receipt/public-car parsing tests and actual driver-form/passenger-trip plus admin-review browser assertions exercise the new UI. Prior browser assertions remain; only the exact intentionally rejected vehicle-review 409 is added to the existing console error allowlist after verifying its response. Browser GPS is emulated; physical phones and native dialer acceptance remain separate.
